\section{Deployment Plan}
\label{sec:future:deployment}

The proposed system is designed for single-process deployment on commodity
hardware. The deployment plan for Phase Two covers two contexts: the local
laptop deployment used during the user-evaluation study described in
Section~\ref{sec:future:eval}, and the longer-term server-side deployment
that supports continued operational use after the study completes. Both
deployment contexts run the same code base and read the same on-disk
warehouse; only the surrounding process configuration differs.

\subsection{Local deployment}
\label{sec:future:deployment:local}

The proposed system runs as a single application process. The data warehouse
persists on disk at approximately one hundred megabytes, which sits within
the budget recorded in Section~\ref{sec:solution:problem:nonfunctional}.
Cold-start time is dominated by application launch rather than by data
preparation because the aggregate tables are already materialised on disk
at the end of the warehouse build. The configuration is a single environment
file that names the warehouse path and the application port; no network
access is required at run time. This deployment supports the user-evaluation
study and ad-hoc demonstration use without any service-side infrastructure.

\subsection{Server-side deployment}
\label{sec:future:deployment:server}

The same code base supports server-side deployment with multi-user access
by running the application process behind a thin reverse-proxy layer.
Configuration changes are limited to the proxy and to a single environment
variable that flags the runtime as multi-user; the variable enables
URL-based session sharing and disables the single-tenant assumptions in the
cache layer. No source-code changes are required to move between local and
server-side deployment, which keeps the demonstration build identical to the
production build and removes a class of deployment regressions.

\subsection{Operational refresh}
\label{sec:future:deployment:refresh}

The warehouse is refreshed offline. A scheduled task reruns the
preprocessing pipeline of Chapter~\ref{chapter:solution} against newly
arrived raw inputs and replaces the on-disk warehouse atomically when the
rebuild completes; the application is not stopped during the refresh, but
a brief read-only window applies while the swap is in progress. The refresh
cadence is parameterised; daily refresh is the planned default after the
user-evaluation study, with weekly and on-demand refresh available as
alternative settings for low-traffic and one-shot analytical use.
