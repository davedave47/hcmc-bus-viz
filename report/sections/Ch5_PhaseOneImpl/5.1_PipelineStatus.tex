\section{Pipeline Status}
\label{sec:impl:pipeline}

Phase~One closes with two artefacts running against the same on-disk
warehouse: the source-to-parquet pipeline that produces the warehouse,
and the running application that consumes it. The pipeline implements
the full Medallion architecture specified in
Chapter~\ref{chapter:solution} --- Bronze (twenty-four raw views over
preprocessed parquet), Silver (twelve dimension tables and three fact
views), and Gold (seven pre-computed aggregate tables that back the
analytical surface). The application reads exclusively from the Gold
tier, so every chart in the catalogue is served by a single
inexpensive query.

\subsection{Components}
\label{sec:impl:pipeline:implemented}

Five components of the data pipeline are present in the Phase~One
artefacts. Together they normalise the raw release files into columnar
storage, partition the two largest streams by calendar day, correct
one mislabelled field discovered during exploratory work, register a
uniform view layer that downstream warehouse layers will consume, and
profile the full set of raw tables to surface data-quality issues
before Phase~Two layers depend on them.

\begin{itemize}
  \item \textbf{Raw view registration.} About twenty-four columnar
    parquet views are registered automatically when the analytical
    engine \cite{duckdb} opens the warehouse, covering the
    Automated Fare Collection (AFC) stream, the Global Positioning
    System (GPS) stream, and the shared master tables of stops and
    vehicle-to-route mappings.
  \item \textbf{Source-to-parquet normalisation.} The raw
    comma-separated value files released with the dataset are
    converted to columnar parquet files with explicit per-column type
    casting. The conversion is idempotent: rerunning the conversion
    against the same raw inputs produces byte-identical parquet
    outputs, and rerunning it against a newer raw batch overwrites
    only the parquet files whose source has changed. The dataframe
    operations of the conversion step are written against the Polars
    engine \cite{polars}.
  \item \textbf{Calendar-day partitioning for the two largest streams.}
    The boarding-event stream and the payment-event stream are written
    as one parquet file per calendar day. The ninety-day AFC window
    thus yields ninety boarding-event files and ninety payment-event
    files, which the analytical engine can prune on a date predicate
    at query time without scanning the full set.
  \item \textbf{Mislabel correction for the cash payment field.} The
    literal label \texttt{Ti\^en m\d{a}t} in the raw payment stream
    was found, during preprocessing inspection, to also cover
    smartcard balance deductions, not only physical cash payments.
    The preprocessing step distinguishes the two modes by writing the
    smartcard subset into a separate column, so that downstream
    payment-channel breakdowns count each mode correctly.
  \item \textbf{Programmatic profiling pass.} A single Python script
    traverses every raw table, characterises each column, validates
    coordinate, speed, and uniqueness constraints, and computes the
    directional joinability between every pair of tables that share a
    column name. The pass writes three machine-readable reports and
    nine figures, and surfaced the data-quality observations recorded
    in Table~\ref{tab:dataset:quality} and the cross-source joinability
    findings recorded in the same table.
\end{itemize}

\subsection{Application Surface}
\label{sec:impl:pipeline:app}

The Phase~One demo is a single-process Python application that serves
the analytical surface specified in Chapter~\ref{chapter:solution}. It
is composed of four layers that match the stack catalogued in
Section~\ref{sec:foundations:tools}.

\begin{description}
  \item[Query layer.] A thin connector module opens the on-disk
    warehouse read-only at process start and exposes a serialised
    \texttt{query()} helper protected by a single mutex; the warehouse
    is opened against the on-disk file rather than against an
    in-memory copy so that the demo can be restarted without
    re-loading the parquet inputs.

  \item[Aggregate layer.] One Python module per analytical theme
    (\emph{schools}, \emph{spatial}, \emph{health}) contains the
    aggregate SQL queries that feed every chart of that theme. Each
    aggregate function is decorated with a process-local
    least-recently-used cache so that the second request for the same
    chart resolves below ten milliseconds; the eight verified
    universities and the fourteen Metro Line~1 stations are hand-coded
    into the same module as Python constants so the school-attribution
    and the bus-to-metro queries remain repeatable.

  \item[Chart layer.] One Plotly-figure builder per chart in the
    catalogue lives in a per-theme charts module. A single style
    helper, \texttt{charts.style.figure()}, applies the locked visual
    invariants of Section~\ref{sec:solution:interaction} as
    construction-time defaults; action titles and supporting subtitles
    are emitted by the surrounding HTML template rather than as figure
    titles so that the figure fills the canvas and the title is not
    duplicated between chart and caption.

  \item[Application layer.] FastAPI \cite{fastapi} routes
    each themed page through Jinja2 \cite{jinja2} templates that
    inherit from a single base layout. HTMX \cite{htmx}
    attributes on the per-card rail issue partial requests that swap
    the canvas content without a full reload; the URL state is pushed
    into the browser history on every swap so a card-and-chart can be
    deep-linked. The Tết story page is delivered through the same
    application layer with Scrollama \cite{scrollama} steps wired to
    the scene specification.

  \item[Validation harness.] A standalone harness runs forty-one
    integrity checks against the built warehouse and is invoked at the
    end of every build (it halts the build on any failure). The checks
    are grouped into table presence (every Silver dimension and Gold
    aggregate exists), row-count bounds (the fixed dimensions have the
    expected cardinality), key uniqueness (the 1:1 dimensions
    \texttt{dim\_route}, \texttt{dim\_trip}, \texttt{dim\_school\_stop}
    have no duplicate join keys), the lossless Bronze-to-Gold chain
    (the Gold boarding count equals the raw 17{,}883{,}623), referential
    integrity (every Gold foreign key resolves into its dimension),
    and domain and null checks (the fare-class domain, the stop bounding
    box, the nine-day T\^et tag in \texttt{dim\_date}). The Phase-One
    warehouse passes all forty-one checks.
\end{description}

\subsection{Reproducibility}
\label{sec:impl:pipeline:reproducibility}

The pipeline as implemented is reproducible from the raw inputs
alone: a single command rebuilds the Bronze tier from the source
files, and a second command (\texttt{python -m demo.warehouse.build})
rebuilds the Silver and Gold tiers from Bronze. The full
Bronze\(\rightarrow\)Silver\(\rightarrow\)Gold build completes in
approximately five seconds on the local workstation. The pipeline
does not require network access at run time: every dependency, from
the source release files to the Python packages of the analytical
engine, is present locally before the build is invoked. Idempotence
is guaranteed because every output is written through atomic file
replacement, with the input file inventory captured in a manifest
written alongside each output; a rerun against the same inputs
therefore produces byte-identical outputs.

The application surface is reproducible from the warehouse alone. The
demo starts with a single command, \texttt{uvicorn demo.main:app}, and
reads the warehouse read-only on first request; the chart catalogue
warms its caches at the latency reported in
Section~\ref{sec:impl:eval} and is then operationally bounded by the
DuckDB query plan against the underlying parquet files.

Byte-identical outputs require that the libraries that produce them
are pinned to specific versions. Phase~One pins the analytical engine
to DuckDB~1.1, the dataframe library to Polars~1.6, the application
framework to FastAPI~0.115 with the Jinja2~3.1 template engine, HTMX
to version~2.0, the visualisation library to Plotly~2.35 (the version
that introduced the MapLibre-backed map traces used by the spatial
theme), Scrollama to version~3.2, and the H3-py geospatial indexing
library to version~4.1. The pin set lives in a project-level
\texttt{requirements.txt} regenerated whenever a library is upgraded,
and the warehouse-build manifest records the resolved versions
alongside the input file inventory so that a rerun under a different
pin set is flagged rather than silently producing different outputs.
