\section{Layered Architecture}
\label{sec:foundations:layered}

Analytical workloads on operational data benefit from separating
concerns into discrete layers between the raw inputs and the
analytical surface. The Medallion pattern from
\cite{databricksMedallion} popularised this idea as three layers ,
Bronze, Silver, and Gold; and the proposed system adopts that
three-tier vocabulary at the architectural level. The internal
organisation of the Silver tier and the materialisation policy of
the Gold tier are design choices the project makes inside the
canonical layout, and Section~\ref{sec:solution:architecture}
records the specific instantiation. The canonical three-layer form
gives each of three recurring concerns (schema heterogeneity,
identifier reconciliation, and query-time efficiency) a single home
in the warehouse, as the medallion subsection below describes.

\subsection{Medallion Pattern}

The canonical medallion pattern defines three layers, sometimes called
Bronze, Silver, and Gold. The Bronze layer holds the raw input data as it
arrives from each source, with only the lightest of transformations
applied to make the data readable; its concern is schema heterogeneity,
that is, accepting whatever shape each source happens to emit without
forcing a uniform model on it at ingestion time. The Silver layer applies
conformed definitions: entities that appear in multiple sources under
different identifiers are reconciled, dates and times are normalised to a
common representation, and the data is cast into the shape an analyst
would draw on a whiteboard. Its concern is identifier reconciliation. The
Gold layer holds aggregated, query-ready tables that correspond directly
to the questions the analytical surface needs to answer; its concern is
query-time efficiency, that is, ensuring that any chart the user requests
can be served by a single inexpensive query rather than by a long chain
of joins and aggregations evaluated on demand.

\subsection{Design Trade-offs}

The layered idea adapts to different workloads, and the choice of how
many layers to introduce and where to draw the boundaries between them is
a design decision rather than a fixed prescription. A first trade-off
concerns how the analytical surface is used. An open-ended analytical
workload, in which analysts write ad-hoc Structured Query Language (SQL)
against a flexible warehouse, tolerates on-demand aggregation: the
warehouse cannot pre-compute every possible query, so it pre-computes a
small set of conformed facts and dimensions and lets each user query
materialise its own result. A fixed analytical catalogue, in which a
known set of charts is rendered by an application, rewards
pre-computation: every chart corresponds to a known query, and the cost
of materialising the result of that query once at build time is repaid
many times over each time a user opens the chart.

A second trade-off concerns the number of layers itself. Too few layers
collapses concerns that ought to be addressed separately, so that a
schema change in one source forces edits across the entire pipeline and
the meaning of a column at the analytical surface depends on details of
how the source emits it. Too many layers adds maintenance cost without
analytical value: each additional layer introduces another set of
materialised tables to keep in sync with the layers above and below it,
without necessarily improving the queries the analytical surface
ultimately serves. A practical architecture introduces exactly as many
layers as are needed to give each concern a single home, and no more.
